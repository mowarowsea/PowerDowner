# PowerDowner ロードマップ

## 目指す状態

> 初期設定さえ済ませたら、あとは放っておくだけ。
> 「最新刊がダウンロード出来たよ！」という通知が来るのを待つだけ。

人間が出てくるのは (1) 監視対象の登録と (2) どうしても人間判定が必要なときだけ。
それ以外は全部システムが回す。以下はそのための構想と、**今のコードのどこが受け口になるか**。
まだ実装していないが、ここに書いた前提を壊す変更は入れないこと。

## 1. 起動・終了・再起動は LocalLauncher に任せる

`C:\Users\seamo\LocalLauncher`

### 今できていること

PowerDowner を 1 個登録すれば足りるようにしてある。aria2 も JDownloader も
PowerDowner が子プロセスとして起動し、終了時に自分で片付ける。

```yaml
  - id: powerdowner
    name: PowerDowner
    description: URL を投げるだけのダウンロード司令塔
    command: "start.bat"
    cwd: "C:/Users/seamo/PowerDowner"
    stop_command: "scripts\\stop-jd2.cmd"
    url: "http://100.121.83.66:3939"
    health_url: "http://127.0.0.1:3939/api/health"
    require_url: true
    icon: "⬇️"
    profiles: [mowa]
```

- `start.bat` … LocalLauncher からの起動口 (中身は `npm start`)
- `GET /api/health` … 死活監視用。PowerDowner 自体が生きていれば 200 を返す。
  各エンジンの状態も入っているので、落ちているものがあれば画面を見なくても分かる
- `stop_command` … LocalLauncher が node をハードキルすると JD2 の終了処理が走らない。
  headless の JD2 は**画面もトレイも無いので居座っても気づけない**。その保険

### 守るべき前提

- **PowerDowner はフォアグラウンドで走り続けるプロセスであること。** デーモン化して
  即 return するようにすると LocalLauncher が生死を見失う
- **SIGINT / SIGTERM で JD2 と aria2 を止めること。** `src/index.ts` の `shutdown()`
- **起動時に既存の JD2 を引き継ぐこと。** `Jd2Engine.start()` は API が応答すれば
  起動をスキップする。ハードキル後の再起動でも二重起動にならないのはこのため
- **対話的な入力を求めないこと。** 初回セットアップも含めて全部設定ファイルで済ませる

## 2. DryEyes が見つけた新着を自動投入する

`C:\Users\seamo\DryEyes` (changedetection.io + BFF)

### やりたいこと

指定ページを監視 → ダウンロードリンクが増えていたら PowerDowner に投入 →
落ちたファイルを日本語タイトルにリネーム。

### 責務の境界

**「相手には原理的に持てない情報」で切る。**

| | 持っている情報 | 持てない情報 |
|---|---|---|
| DryEyes | 前回スナップショット、既読位置、XPath、監視の文脈 | どのホスターなら落とせるか / もう持っているか |
| PowerDowner | ホスター実績表、エンジン振り分け、リトライ、保存先 | そのページで何が「新しい」のか / 手元に何があるか |
| **pinax** | **手元の棚に何があるか**、欠番、完結、書誌と書影 | どこから落とすか / 何が新しく出たか |

```
DryEyes                                        │  PowerDowner
定期チェック → 差分 → 増分の要素を特定          │
  → その要素配下の <a href> を全部拾う          │
  → 1 件 = { メタ, urls[] } に束ねて候補に積む  │
  → 人が承認 ─── POST /api/jobs ─────────────▶ │ urls[] をホスター表で選別・優先度付け
                                               │  → 棚 (pinax) に聞く (所持済みならスキップ)
                                               │  → 落とし中のジョブがあれば合流
                                               │  → 先頭で挑戦、駄目なら次のミラー
                                               │  → 完了 → リネーム → 通知
```

**DryEyes はリンクらしきものを全部渡すだけで、選別しない。** ホスターの知識を DryEyes に
複製すると README の実績表が二重管理になる。「ルーティングは `src/router.ts` に閉じる」を
そのまま守れる形にしておく。

### 差分テキストから URL は取れない

changedetection.io のスナップショットはテキストなので、**増えた行が分かっても href は残らない**。
グローバル設定 `render_anchor_tag_content` を有効にすれば URL 混じりのテキストになるが、
全監視の差分が汚れて人が読めなくなるので採らない。

差分は「どの行が増えたか」の検知だけに使い、**URL は DryEyes の `browserRender.ts` で
実ページを開いて XPath 配下の `<a>` から取る**。`hasAnySelectorMatch()` と同じ仕組みで書ける。

### 受け渡しの形

今の受け口はこうなっている:

```
POST /api/jobs  { userId, urls: string[], destDir? }
```

URL ごとに別ジョブになるので、**同一ファイルのミラーを表現できない**。ここが唯一の必須拡張。
`urls` は既存互換として残し、`items` を足す:

```
POST /api/jobs
Authorization: Bearer <token>
{
  userId, destDir?,
  items: [
    {
      urls: ["https://mexa.sh/...", "https://dailyuploads.net/..."],   // 同一ファイルのミラー
      sourceKey: "<watch-uuid>:<行のハッシュ>",
      source: "dryeyes:<watch-uuid>",
      meta: {
        title: "作品名", author: "著者", volume: "3",
        rawText: "[著者] 作品名 第03巻"      // 抽出前の生テキスト
      }
    }
  ]
}
```

**`rawText` は必ず添える。** 抽出ルールは必ずどこかで外れる (表記変更、作画と原作で 2 人、
シリーズ名と巻数がくっつく)。生テキストが残っていれば「抽出が空なら rawText をそのまま使う」
フォールバックが書けるし、後からルールを直して再パースもできる。

### 画面から作品として登録する

DryEyes を通さない手投入 (完結した作品、1 冊だけのシリーズ) も、**同じ道を通す**:

```
POST /api/jobs
{ userId, urls, destDir?, item: { title, author?, volume? } }
```

サーバー側で `items` の形に組み立て直してから `queue.addItems` に渡す。
`volume` があれば `urls` は同一ファイルのミラー、無ければ 1 行 1 件に割り、
`rawText` に URL のファイル名を入れて巻数を読ませる。`source` は `manual`。

**判定を 2 通りにしないこと。** 所持の突き合わせ・ミラーの並べ替え・リネームが
「どこから入れたか」で変わると、手で入れた分だけ二重に落ちる、という壊れ方をする。
トークンを要求しないのは、素の `urls` 投入 (画面から) と同じ口だから — `items` 形式
そのものは DryEyes 用の契約なので、トークン必須のまま触らない。

### 2 種類のキー

混ざりやすいが、目的の違う 2 つが要る。

| キー | 意味 | 持ち主 |
|---|---|---|
| `sourceKey` = `<watch-uuid>:<行のハッシュ>` | 同じ監視から同じ行を二度送らない | DryEyes (投入ポインタ) |
| `seriesKey` + `volume` | **サイトをまたいだ同一性** | PowerDowner (合流) / pinax (所持) |

サイト A とサイト B で同じ巻が出た時、`sourceKey` は必ず別物になるので防げない。
同一性の判定は PowerDowner が正規化して行う。**そこに置くのは「実際に落ちたか」の真実を
PowerDowner しか持っていないから。** DryEyes 側で止めると、投入したが全ミラー失敗していた
ケースで二度と落ちてこなくなる。

正規化はこの形:

```
seriesKey = title.normalize('NFKC').toLowerCase()
              .replace(/[\s　_\-–—・,.、。!?！？'"'"()（）\[\]【】]/g, '')
volume    = "第03巻" "第3巻" "(3)" "vol.3" → 3 (数値に落とす)
```

- **作者名はキーに入れない。** 片方のサイトに作者表記が無いことがあり、入れると同じものが別扱いになる。
  表示とリネームには使う
- **サブタイトルは含める方に倒す。** サイトによって付いたり付かなかったりするが、
  誤合流より再ダウンロードの方が被害が小さい
- **巻数が取れなければ合流しない。** キーが作れない時は重複判定を諦めて素直に落とす

### 2.5 取得済みの判定は pinax に聞く (台帳を捨てた経緯)

**2026-09-14 に `items` 表 (取得済み台帳) を捨てた。** 後から「なぜこの形なのか」が
分からなくならないよう、いきさつをここに残す。

#### 最初はこうだった

PowerDowner が自分で台帳を持っていた。ジョブ履歴とは別テーブルにしたのは、
**サイト A で落とした 1 か月後にサイト B へ同じ巻が出る**のが普通に起きるからで、
「ジョブは消せても所持は残る」という関係にしたかった。

```
items:
  userId, seriesKey, volumeFrom, volumeTo
  status  -- 'have' (PowerDowner を通さず入手済み) | 'done' (完走した) | 'pending' (落とし中)
  title, author, jobId, source, rawText, mergedFrom[]
```

投入時は `status IN ('done','have')` を見てスキップ、`pending` があれば合流。
手元のフォルダを走査して `have` を流し込む口 (`POST /api/items/scan`)、
範囲で登録する口 (`POST /api/items`)、壊れた行を人が直す管理画面まで作った。

#### 何が問題だったか

**台帳はダウンロードの記録であって、棚の姿ではない。**

- 手で NAS に置いたもの、落とす前から持っていたもの、消したものが映らない
- 「持っている」と言い切る場所なので、**間違った行が 1 つあるだけでその巻は永久に
  落ちてこない。** 投入側からは「スキップされた」としか見えない

実際に踏んだ壊れ方が 3 つある:

| 壊れ方 | 何が起きたか |
|---|---|
| 中身の無いファイルで `done` になった | 持っていないのに二度と落ちてこない |
| 作品名が無いまま投入され、生の文字列からキーが作られた | 別サイトの同じ巻と噛み合わない。同じ作品が複数のキーに割れる |
| `pending` の行がジョブより長生きした | その巻の投入が全部この行へ合流して、何も起きない |

管理画面を足して人が直せるようにしたが、それは**症状への手当て**で、
「台帳が棚を映していない」という素性は変わらなかった。

#### なぜ捨てられるようになったか

蔵書カタログ **[pinax](../../pinax/README.md)** が立った (2026-09)。pinax は台帳ではなく
**ファイルそのものを正**にして、NAS の棚を毎回読む。488 作品 4945 ファイルが載っていて、
`POST /api/own` で「この巻もう持ってる?」に答える。

**だから、既に落としたファイルを PowerDowner で管理しなくてよい。**
手で置いたものも、消したものも、棚を読めば分かる。台帳を持ち続ける理由は無くなった。

段を踏まずに一息で寄せたのは、**PowerDowner をまだ本格運用していなかった**から
(影運転で差分を見る手もあったが、守るべき運用データが無かった)。`items` 表は
DROP し、ジョブに結び付いていた行の巻の解釈だけ jobs へ移した (31/32 件)。

#### 台帳の仕事のうち、1 つだけ残った

**「今落としている最中の巻」は棚を見ても分からない。** まだファイルが無いので、
pinax は「持っていない」としか答えられない。ここを落とすと、同じ巻が別サイトから
来るたびに二重に落ちる。

そこで `jobs` に `series_key` / `volume_from` / `volume_to` を持たせた
(投入時に読んだ解釈をそのまま焼く)。判定に参加するのは:

| ジョブの状態 | 扱い |
|---|---|
| `queued` 〜 `waiting_*` | **合流。** ミラー候補として既存ジョブに足す |
| `done` | **スキップ。** 棚のスキャンは 3 時間おきなので、載るまでの隙間をここで埋める |
| `failed` / `canceled` | 参加しない (落とし直せないと困る) |

これで**落とし直したい時はジョブを消せばよくなった。** 台帳の頃の
「消し忘れた行がその巻を永久に止める」壊れ方は、構造から消えている。

#### 聞けない時は落とす

pinax が止まっていても投入は通る。答えが返らなければ「持っていない」に倒す —
黙って持っていることにすると、その巻は二度と落ちてこない。
**もう一度落ちる方が被害が小さい。** 同名のファイルは `uniqueName` が
`... 第03巻 (2).rar` に逃がすので、落とし直しても手元のものは潰れない。

#### 残っている食い違いの種

- **ローマ字と日本語は噛み合わない。** `Saihate_no_Paladin_v01.rar` で投入すると、
  棚に「最果てのパラディン」があっても「持っていない」と答える (2026-09-14 に実測)。
  台帳の頃も同じだったので後退ではないが、pinax 側で読みを突き合わせる話が
  [pinax の ARCHITECTURE 8.1](../../pinax/docs/ARCHITECTURE.md) にある
- **台帳はユーザー単位だったが、棚は根 (フォルダ) 単位。** ユーザーごとに棚を分けたいなら
  pinax の `roots` を分ける。合流の判定だけは今もユーザーごとのジョブを見る
- **DryEyes の「これは既に持っている」登録は行き場が無くなった** (`POST /api/items` を
  廃止した)。本来は「pinax の管理フォルダに既にあるので不要」の意思表示で、
  今は棚が同じことを答える。DryEyes 側の呼び出しは次の段で片付ける。
  一方 `POST /api/items/check` は**口を残して中身だけ pinax 委譲にした**ので、
  候補一覧の「もう持っている」の印は向こうを直さずに動き続ける

### 保存先のフォルダ構成 (2026-09-10 に確定)

```
保存先      \\192.168.3.30\disk1_pt1\manga   (NAS。ユーザーの既定フォルダ)
作品フォルダ [{著者}] {作品名}
ファイル名   [{著者}] {作品名} 第{nn}巻.{拡張子}
             [{著者}] {作品名} 第{nn}-{nn}巻.{拡張子}   ← 範囲もの
```

**済** — 組み立てと読み戻しは `src/naming.ts`、実行は `Queue.onDone`。
細かい振る舞い (連番・分割書庫・話/巻・失敗時) は README「落ちた後の整理」にまとめてある。

決めた結果、こうなっている:

- **ユーザーごとに保存先を分ける。** 受け口は既存のまま (`User.defaultDir`)。
  合流の判定もユーザーごとのジョブを見るので、同じ作品を 2 人が追いかけても
  互いに弾き合わない (所持そのものは棚が答える。ユーザーで分けたいなら pinax の
  `roots` を分ける)
- **著者を `seriesKey` に入れない。** ここが今回いちばん効いた修正で、入れると
  ファイルから起こしたキーだけが `著者+作品名` になり、DryEyes から `title: "作品名"` で
  来た同じ巻と永久に噛み合わない (手元にあるのに落とし直す)。
  書く側 (`naming.planName`) も読む側 (棚の pinax) も、著者を外してからキーを作る
- **テンプレートは設けない** (下の「リネーム」の案は取り下げ)。自由に書けるようにすると
  読み戻せない名前を人間が書けてしまい、上と同じ壊れ方をする。切りたい人向けに
  `rename.enabled` / `rename.folder` の 2 つだけ用意した

まだ確かめていないこと:

- **UNC パスに各エンジンが書けるか。** `path.isAbsolute()` は UNC を絶対パスとして通すので
  `resolveDest` は素通りするが、aria2c / JD2 (Java) / ブラウザのダウンロード先として
  実際に書けるか、資格情報が要るかは試していない。**実機で最初に踏むならここ**
- リネームは `fs.renameSync` なので、保存先と同じボリュームの中で動く前提。
  ダウンロード先を別ドライブにするなら跨ぎ (EXDEV) の対応が要る

### 巻数は範囲で持つ

`1-6巻.rar` のように 1 ファイルが複数巻を含むものがある。**6 件に割らない** —
ファイルは 1 つなのに行が 6 つできて、ジョブとの対応も削除も破綻する。
`volumeFrom`/`volumeTo` の範囲として持ち、判定は重なりで行う (jobs も pinax の巻も同じ):

```sql
WHERE user_id = ? AND series_key = ? AND volume_from <= ?to AND volume_to >= ?from
```

重なったものの扱い:

| 状況 | 判断 |
|---|---|
| 落としている最中のジョブ | **合流。** `urls` を `meta.mirrors` に追記し、失敗確定なら `queued` に戻す |
| 完全に覆えている (棚が 1-6 巻 → `第3巻`) | スキップ |
| 部分的にしか重ならない (棚が 1-6 巻 → `4-8巻`) | **未所持 (7,8) が残るので落とす** |

**「未所持の巻が 1 つでも残っているなら落とす」が唯一のルール。** 4,5,6 が重複するが、
ファイルを巻単位で切れない以上こうするしかない。落とせば 4-8 のレコードが増え、
1-6 と 2 件で 1-8 をカバーする。**レコードのマージは不要** (判定結果は変わらず、
どのファイル由来かの情報が残る)。表示で畳めばいい。

同じ投入の中に同じものが 2 件混ざることもある (DryEyes が同じ巻を別ページで見つけ、
区切り文字だけ違うファイル名で送ってくる: `Haipa_Infureshon_v03-05s.rar` と
`Haipa Infureshon v03-05s.rar`)。この時点では手元にまだ 1 件もジョブが無いので上の SQL では
気付けず、`decideItems` が投入の中で突き合わせて 1 件目へ寄せる。**ここだけは範囲が完全に
同じものしか寄せない** — 同じ投入に 1-3 巻と 3-5 巻が並ぶのは分割セットが両方公開されている
時で、重なりで寄せると 4,5 巻が落ちてこない。

重複排除ではなく**「同一アイテムへの合流」**として作ると、サイト A で詰まっていた巻が
サイト B の出現で落ちるようになる — ミラー機構 (下の 4) がそのまま効く。

パースの罠:

- **`〜` は NFKC で吸収されない。** 波ダッシュ (U+301C) と全角チルダ (U+FF5E) は別文字のまま。
  `-` `‐` `–` `—` `~` と合わせて範囲区切りは文字クラスで列挙する
- **巻数は後ろから探す。** タイトル自体に数字とハイフンを含む作品がある
- **巻キーワードを必須にする。** `巻` `話` `vol` `第` を伴うものだけ範囲と認める。
  でないと解像度 (1920-1080) や年号を拾う
- `全6巻` `完結` は 1-6 相当として拾う
- 失敗したら `volumeFrom/To = null`。範囲判定に参加せず常に落とす

### 承認フロー

**当面は自動投入しない。** DryEyes が抽出結果を「投入候補」として溜め、画面で確認して
押したものだけ POST する。抽出ルール (URL・作者・巻数) の当たり外れを見てから自動へ
切り替える。投入に失敗しても押し直せばいいので、DryEyes 側にリトライ機構は要らない。

- 監視ごとに「自動 / 確認してから」を持たせ、安定したものから昇格させる
- **巻数の取れない監視 (雑誌・読切) は自動にしない。** 範囲判定に参加できず毎回落ちる
- 一度の投入は 20 件で打ち切ってログに出す。監視を作り直して全増分が新規に見えた時の安全弁

### 認証

投入口ができると「LAN 内の誰でも任意 URL を落とさせられる」口になる (`host` は `0.0.0.0`)。
`config.json` に共有トークンを 1 本置き、`Authorization: Bearer` で検証する。

### スキップと合流は必ず見せる

所持済みで弾いた時に黙って捨てると「新刊が出たのに落ちてこない、DryEyes が壊れた？」の
切り分けができなくなる。`skipped` (所持済み) として一覧に残すか、最低でも `seriesKey` と
理由をログに出す。合流も同様に「他 2 サイトから合流」と出す。

正規化は必ずどこかで誤合流する (修正版、画質違い、同名別作品の第 1 巻同士)。逃げ道を 2 つ:

- **`force` 付きの再投入。** 「これは別物だ」と人が言えば同一性判定を無視して新規ジョブを作る
- 「持っていることになっているが実は壊れていた」の復旧路。**済** —
  落とし中・落とし済みはジョブを消せば判定から外れる。棚の側の食い違いは
  pinax の画面 (要確認・エクスプローラで開く) で人が見て直す

### リネーム

**済** (2026-09-10)。実行場所は `Queue.onDone`。ここは既に「完了時に一度だけ通る」場所なので、
後処理 (リネーム、通知、次の候補への引き継ぎ) は全部ここに集約できる。

当初案の `rename.template` / `rename.templateRange` は**取り下げた**。テンプレートを設定にすると、
棚 (pinax) が読み戻せない名前を人間が書けてしまい、手元にあるのに「持っていない」と
判断して二重に落とす。形式は `src/naming.ts` に固定し、`rename.enabled` / `rename.folder` の
2 つだけを設定に出してある。

**ファイル名として安全にするのは PowerDowner の責務。** `\ / : * ? " < > |` (全角に倒す)、
長さ制限、末尾のピリオド、予約名 (CON, NUL) — Windows のファイルシステムを触る側の問題で、
DryEyes は生の値を渡すだけにする。元の拡張子は保つ。ダウンロード中は元のファイル名のまま。

### 実装の順序

1〜3 は DryEyes 無しで `curl` だけで検証できる。**抽出ルールの当たり外れ (4) と
重複判定の正しさ (1〜3) を別々に潰す**のが狙いで、両方いっぺんに動かすと切り分けができない。

| # | 場所 | 内容 | 状態 |
|---|---|---|---|
| 1 | PowerDowner | `items` 形式 + トークン検証 + 所持判定 + 巻数/範囲パース + 合流判定 | **済** (`src/volume.ts`, `src/library.ts`, `src/pinax.ts`) |
| 2 | PowerDowner | ミラー切替 (下の 4)。失敗時とホスト上限時の 2 経路 | **済** (`src/mirrors.ts`) |
| 3 | ~~PowerDowner~~ pinax | 手元にある巻の把握 | **pinax が引き取った** (棚を毎回スキャンする。上の 2.5) |
| 4 | DryEyes | 増分要素から `<a href>` とメタの抽出 + 候補テーブル | |
| 5 | DryEyes | 候補一覧 UI と投入ボタン | |
| 6 | PowerDowner | 完了時リネーム + ntfy 通知 (下の 3) | リネームは**済** (`src/naming.ts`)。ntfy は未着手 |

### 守るべき前提

- **`Job.meta` は `Record<string, unknown>` のまま自由に保つこと。** ここを型で固めると
  DryEyes 由来の情報 (`item`, `mirrors`, `tried`, `source`) を運ぶ場所が無くなる
- **同一性の判定は PowerDowner の 1 か所だけで行うこと。** DryEyes 側にも同じ判定を置くと、
  正規化ルールを直した時に両方を直す羽目になる
- **正規化キーの組み立ては PowerDowner に閉じること。** DryEyes が渡すのは
  `title` / `volume` / `rawText` まで。ただし**キーの規則そのものは pinax と同一**で
  なければならない (`src/volume.ts` はあちらへ移植済み) — 片方だけ直すと、棚が
  「持っている」と言う巻をこちらが「持っていない」と言い、静かに二重取得が始まる
- **所持の記録を PowerDowner に持たないこと。** かつて `items` 表でやって捨てた (上の 2.5)。
  「ジョブを消したら所持情報まで消える」問題は、棚を毎回読む pinax が引き受けたので
  もう起きない。ここに台帳を戻すと、**棚と食い違う 2 つ目の真実**ができる

## 3. 完了したら ntfy で通知

ntfy は既に LocalLauncher に登録済み (`http://127.0.0.1:8085`、DryEyes と共用)。

### 受け口の見通し

- `bus.on('job')` で `status === 'done'` を拾えば、エンジンを問わず完了を捕まえられる。
  aria2 / JD2 / ブラウザのどれで落ちても同じ 1 か所で済む
- 送信そのものは `src/notify.ts` に足す。今の `toast()` は Windows ローカル通知だけなので、
  「宛先を複数持つディスパッチャ」に育てるのが自然:

```
notify({ kind: 'done' | 'human' | 'failed', title, body, jobId })
  → Windows トースト (PC の前にいる時)
  → ntfy      (スマホ。DryEyes と同じくユーザーのトピック配下へ)
```

- 通知したいのは完了だけではない。**人間待ちも通知しないと放置運用が成立しない**
  (黙って止まったジョブに気づけない)。`Queue.onWaitingHuman` は既にトーストを出している
- **DryEyes と通知を二重に出さないこと。** 監視の更新自体は DryEyes が既に ntfy へ飛ばしている
  ので、「新着が出た」「候補が溜まった」は DryEyes の担当。PowerDowner が出すのは
  ジョブの完了・人間待ち・失敗だけに絞る
- ntfy の `click` に PowerDowner のジョブ URL を載せれば、通知タップでそのジョブに飛べる。
  DryEyes が同じことをやっているので作りを揃える

**守るべき前提**: 通知の送信を各エンジンに散らさないこと。全部 `bus` 経由で拾う。

## 4. ミラーの優先度による自動選択

同じファイルが複数のアップローダに置かれている時、事前に決めた優先度の高い方から取る。

### 設計の見通し

今の `Job` は URL を 1 本しか持たない。ここが一番大きな変更点になる。

```
Job.url            … 今まさに試している URL (今の意味のまま)
Job.meta.mirrors   … 未試行の候補 URL を優先度順に並べたもの
Job.meta.tried     … 試して駄目だった URL と理由
```

- 優先度は `config.json` にホスト名の並びで持つ (`mirrors.priority: ["dailyuploads.net", ...]`)。
  実績表 (README) がそのまま初期値になる
- 投入時に候補を並べ替えて先頭を `url`、残りを `meta.mirrors` に入れる
- **切り替え点は `Queue.onFailed`。** ここで `meta.mirrors` が残っていれば、失敗として
  確定させずに次の候補で `queued` に戻す。既に「ブラウザ経路へ落とす」分岐
  (`onNeedsBrowser` → `toBrowser`) があるので、同じ形で書ける
- 人間待ちで詰まった時も次の候補に回したい。ただし**勝手に見捨てると人間の操作が無駄になる**
  ので、タイムアウトを置いてから移ること

### もう 1 つの切り替え点: ホストの同時ダウンロード上限

**失敗しないまま進まない状態がある。** 無料アップローダは同時ダウンロード数を 1 本に
絞っていることが多く、2 本目以降に「Download limit reached or wait until next download
can be started」と言ってくる。JD2 はこれを失敗にせず待ち行列に置いたままにするので、
`onFailed` は永遠に呼ばれない。5 件投入すると 1 件だけ流れ、残りが 0 B/s で並ぶ。

ミラーがあるのだから待つ必要はない。`Queue.onHostLimited` で**空いている別のアップローダ**
へ回す。失敗経路とは扱いを 3 点変える:

| | 失敗 (`onFailed`) | 上限 (`onHostLimited`) |
|---|---|---|
| 候補の選び方 | 優先度順に次の 1 本 | 優先度順のうち**他のジョブが使っていないホスト**の先頭 |
| 今の URL | `meta.tried` へ (二度と使わない) | `meta.mirrors` の**末尾へ回す** (時間で空くので使い切らない) |
| 候補が無い時 | 失敗を確定 | **確定させず待つ。** 上限は待てば解ける |

- **ふさがっているホストを避けるのが要点。** 単に優先度順の次を取ると、上限に当たった
  ジョブが揃って同じホストへ移り、そこでも詰まって候補だけを消費する
- **すぐには移さない** (`mirrors.hostLimitWaitSec`、既定 60 秒)。上限は数分で空くことがあり、
  実績のあるホストを毎回手放すと落ちにくいほうへ流れる
- 判定は JD2 の status 文字列 (`HOST_LIMIT`)。ローカライズされていて当たらなければ、
  何もせず従来どおり待つ — 誤検知で実績のあるホストを手放すほうが痛い
- 移す前に `detach` する。JD2 に残したままだと枠を掴んだままになる

### 候補はどこから来るか

`meta.mirrors` の出所は 2 つ。どちらも同じ経路に乗る。

- 人が UI で複数の URL を貼った時
- **DryEyes が 1 件の新着として束ねた `items[].urls`** (上の 2)

さらに、**候補は後からも増える。** 別サイトの監視から同じ巻が投入された時、巻の重なり判定で
既存ジョブに合流して `meta.mirrors` に追記される。失敗確定済みだった場合は `queued` に戻す —
サイト A で詰まっていた巻がサイト B の出現で落ちるのはこの経路。

**投入されたジョブの完遂責任は PowerDowner が持つ。** 全ミラーを試して駄目でも DryEyes に
差し戻さない。差し戻すと DryEyes 側に「投入したが失敗した」という状態が生まれ、
リトライの責任が両側に散る。失敗は通知して人に見せ、`retry` で再開できれば足りる。

**守るべき前提**:
- `Job` は 1 ファイル 1 レコードのまま保つこと。ミラーごとにジョブを作ると
  「どれが本命か」が UI からも通知からも分からなくなる
- 失敗の確定 (`status = 'failed'`) は `Queue.onFailed` の 1 か所だけで行うこと。
  ここが候補切り替えの唯一の差し込み口になる

## 全体を通して壊してはいけないもの

1. **エンジンは差し替え可能なままにする。** `aria2` / `jd2` / `browser` はどれも
   `start / stop / add / cancel / status` を持つ。ルーティングは `src/router.ts` に閉じる
2. **人間が必要な場面を増やさない。** 増やすなら必ず通知とセットにする
3. **有料サービスに依存しない。** Debrid もプレミアムアカウントも外部 CAPTCHA ソルバーも使わない
4. **外部に利用中のアップローダを漏らさない。** ファビコンを自前で取っているのはこのため
5. **同一性の判定と正規化は PowerDowner に閉じる。** 「同じファイルか」「もう持っているか」を
   判断できるのは、ホスターの知識とダウンロードの実績を持つ側だけ。DryEyes は見つけたものを
   素直に渡すことに徹する
